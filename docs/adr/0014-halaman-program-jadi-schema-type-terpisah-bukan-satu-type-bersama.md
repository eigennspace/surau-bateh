# Halaman Program jadi enam schema type Sanity terpisah, bukan satu type bersama

Enam Halaman Program (`khitanan`, `dauroh`, `tawajjuh`, `konseling`, `baktiSosial`, `silaturahmi`) punya bentuk dokumen yang identik, dan masing-masing hanya butuh satu instance (singleton) — sama seperti `profilSurau`. Bentuknya yang seragam membuat "satu schema type `program` dengan enam dokumen ber-`_id` tetap" terlihat sebagai pilihan wajar untuk menghindari duplikasi enam file schema yang hampir sama.

Kami memutuskan sebaliknya: **enam schema type terpisah** (`khitanan.ts`, `dauroh.ts`, dst.), masing-masing singleton sendiri, dengan field yang sama ditarik ke helper bersama (`programFields.ts`) — mengikuti pola `eventFields.ts` yang sudah dipakai untuk `recurringEvent`/`oneOffEvent`. Alasannya teknis: mekanisme penguncian singleton yang sudah ada di `sanity.config.ts` (`SINGLETON_TYPE`/`SINGLETON_ID`, filter `document.actions`/`document.newDocumentOptions`) dikunci per satu nama *type*, bukan per beberapa `_id` tetap dalam satu type. Opsi "satu type bersama" akan memaksa menulis ulang mekanisme itu jadi mendukung daftar `_id` tetap per type — menambah kerumitan pada kode infrastruktur Studio yang sudah teruji, demi menghindari duplikasi field yang sudah bisa diatasi lewat helper biasa. Enam type terpisah juga cocok dengan kalimat ADR [0013](0013-seluruh-konten-sumber-data-migrasi-ke-sanity.md): kontak person "digabung ke dokumen **programnya sendiri**" — tiap program adalah entitas dokumennya sendiri, bukan satu baris dalam koleksi `program`.

Konsekuensi: menambah Halaman Program baru di masa depan berarti menambah satu schema type baru (bukan cuma satu dokumen) — tapi ADR 0013 sudah menetapkan Halaman Program tetap enam rute tetap di kode, jadi penambahan type baru untuk kasus ini diperkirakan jarang terjadi.
