# Situs di-hosting di GitHub Pages dengan domain custom diatur lewat Settings, bukan file `CNAME`

Situs statis (Vite build, tanpa server-side rendering atau API) tidak butuh kapabilitas hosting lebih dari yang GitHub Pages sediakan — kami memutuskan tidak perlu hosting terpisah (Vercel, Netlify, Cloudflare Pages, dll) untuk saat ini, karena repo sudah ada di GitHub, Pages gratis, dan build/deploy sudah otomatis lewat `.github/workflows/deploy.yml` (`actions/upload-pages-artifact` + `actions/deploy-pages`, build type `workflow`, bukan branch `gh-pages` lama). Ini keputusan yang sengaja dibatasi untuk kondisi sekarang, bukan komitmen permanen — kalau ke depannya situs butuh sesuatu yang Pages tidak sediakan (server function, redirect kustom di luar yang GitHub tangani, dll), keputusan ini perlu ditinjau ulang. Domain custom (`suraubateh.web.id`, termasuk `www.suraubateh.web.id` yang di-redirect otomatis oleh GitHub ke apex) disetel lewat GitHub Pages Settings (dapat diverifikasi lewat `gh api repos/eigennspace/surau-bateh/pages`, yang mengembalikan `cname: "suraubateh.web.id"` dan `https_certificate.state: "approved"`) — bukan lewat file `CNAME` yang dikomit ke repo. Ini keputusan sadar, dipilih karena lebih simpel diatur langsung di Settings dibanding memelihara file terpisah. Secara teknis ini valid: untuk Pages berbasis Actions (`build_type: "workflow"`), domain custom tersimpan di konfigurasi repo dan tidak butuh file `CNAME` di source atau artifact build supaya domain tetap hidup antar-deploy — beda dari Pages berbasis branch lama, yang kehilangan domain kalau file `CNAME` tidak ada di branch yang dipublikasikan. Konsekuensinya: konfigurasi domain ini tidak ter-*version-control* — kalau repo pernah dihapus dan dibuat ulang, atau kepemilikan repo dipindah, setting domain harus disetel manual lagi lewat GitHub UI/API, tidak otomatis ikut ter-*restore* dari kode.
